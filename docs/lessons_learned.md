# Lessons Learned

## 2026-10-30 麻雀ルールは記憶で書かない

- 自分の記憶で書いた Mリーグのルール表が、2項目で逆だった（切り上げ満貫・数え役満）
- **次は**: ルールの既定値は、出典 URL と確認日が付いたものだけを要件やエンジンに入れる。一次情報が読めない日は「要確認」として分けておき、エンジンには組み込まない
- 同じ日に 110符1翻 でも同じ失敗をしたため、`.claude/rules/mahjong-rules.md` に昇格した

## 2026-10-30 ローカルで通っても、CI の型チェックは落ちる

- `tsc --noEmit` がローカルでは通り、CI では `Cannot find name 'LayoutProps'` で落ちた。`LayoutProps` などは Next.js が `.next/types` に生成する型で、ビルド前の CI には無い
- **次は**: 型チェックは `npm run typecheck`（`next typegen` → `tsc`）だけを使う。「ローカルで通った」は、新しく clone した環境で同じ順番に通してから言う

## 2026-10-30 端末の文字化けを、ファイルの文字化けと取り違えない

- 公式ページの保存版を Python で読んで端末に出したところ、日本語が化けた。ファイルが Shift_JIS だと思い込んで cp932 で読み直したら、ファイルに書き出した文字列の方が壊れた。実際のファイルは宣言どおり UTF-8 で、化けていたのは Windows の端末出力だけだった
- **次は**: 文字化けを見たら、まず `charset` の宣言とバイト列を確かめる。中身を確かめたいときは、端末に出さずにファイルへ書いて読む（`python -X utf8` を使う）

## 2026-10-30 Vitest で globals を使わないなら、cleanup を自分で呼ぶ

- 画面のテストを2件目から書いたところ、前のテストで描画した画面が残っていて「同じ名前のラジオボタンが複数ある」と落ちた。Testing Library の自動 cleanup は `afterEach` がグローバルにあるときだけ動き、この雛形は `globals: false` だった
- **次は**: `vitest.setup.ts` で `afterEach(cleanup)` を呼ぶ（設定済み）。雛形の画面テストが1件しかない間は、この不具合は表に出ない

## 2026-10-30 スマホ優先で作り、PC を後回しにした（指摘を受けた）

- 要件に「スマホ優先」と書き、PC では細い列を中央に置くだけの画面を作った。user から、スマホ・PC などさまざまなデバイスで使いたいと指摘を受けた
- **次は**: 画面は最初から複数の幅で設計し、確かめる。対応するデバイスと確かめる幅は `docs/requirements.md` の 7 章、手順は `.claude/rules/layout.md`

## 2026-10-30 本番 URL を「200 が返り、見出しが一致した」だけで確定しない

- `mahjong-drill.vercel.app` が 200 を返し、「麻雀点数計算ドリル」の文字列も含んでいたので本番だと報告した。実際は、同じ名前を持つ別の人のアプリだった。本当の本番は `mahjong-drill-phi.vercel.app`
- **次は**: 本番 URL は `vercel inspect <デプロイURL>` の Aliases で確かめる。表示の確認には、このアプリにしかない文言を使う

## 2026-10-30 Windows では TaskStop で dev サーバーが止まりきらない

- `npx next dev` をバックグラウンドで起動して `TaskStop` で止めたが、子プロセスの node が残ってポートを使い続けた。次に起動したサーバーは `EADDRINUSE` で落ち、残った古いサーバーが画面を出していた
- **次は**: dev サーバーを止めたら、`netstat -ano | grep :<port>` でポートが空いたかを確かめる。残っていたら `taskkill //PID <pid> //T //F` で子プロセスごと止める

## 2026-10-30 テストの手牌の書き間違いは、気をつけるより検査で止める

- 符・役のテストで、私が書いた手牌の誤りが続いた。どれもエンジンは正しく、期待値の側が間違っていた
  - 和了牌を二重に入れて枚数が合わない
  - 解釈が複数ある手を、1つしかないと思い込む
  - 和了形になっていない
  - 78 の待ちを辺張と取り違える（両面）
- **次は**: テスト用の手牌は `testHand` で作る。`testHand` は枚数が合わないと例外を投げる。期待値を書く前に、その手の解釈がいくつあるかをエンジンで確かめる

## 2026-10-30 早見表の範囲を、エンジン全体の上限にしない

- `calcScore` が符を早見表の範囲（110符まで）に限っていた。么九牌の暗槓が重なる手は 120符を超え、生成した手の解析中に例外になりうる。まれな手なのでテストに出ていなかった
- **次は**: 「表に載っている値」と「ありえる値」を分けて持つ。入力の検証は「ありえる値」で行い、表の範囲は出題範囲を決めるのにだけ使う

## 2026-10-30 アクセシビリティツリーだけで手牌を読まない

- Chrome DevTools MCP のスナップショットは牌を1列に並べるだけで、手牌・ツモ牌・副露のまとまりが分からない。チーした牌を手の中の牌と読み違え、正しい解説を自分の誤りと取り違えかけた
- **次は**: 画面の手牌を手計算で確かめるときは、`evaluate_script` で `role="group"` ごとに牌を取り出して読む

## 2026-10-30 ダークモードで切り替わる色を、暗い面の上の文字に使わない

- 卓（緑）の上の文字に `text-ivory` を使ったところ、`ivory` はダークモードで暗い色に切り替わるため、卓の上の文字が読めなくなった。ライトモードだけ見ていたら気づかなかった
- **次は**: 色のトークンを「モードで切り替わるもの」と「切り替えないもの」（`on-dark`・`correct-strong`）に分ける。画面を変えたら、ライト・ダークの両方を3つの幅で確かめる

## 2026-10-30 条文の定義を、数値の近道で置き換えない

- 切り上げ満貫を「基本点がちょうど 1920 なら満貫」と実装した。条文は「30符4翻・60符3翻」と翻と符で定めていて、1920 には 120符2翻も入るため範囲がずれた。教材での点検で見つかった
- **次は**: 条文が条件を列挙しているときは、同じ形（翻と符の組）で実装する。計算上同じに見える近道を使うなら、範囲が一致することをテストで確かめる
